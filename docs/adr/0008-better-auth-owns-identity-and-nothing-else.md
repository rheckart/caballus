# Better Auth owns identity, and nothing else

Authentication is a self-hosted Better Auth running against the same Postgres as the application, owning exactly three tables: `user`, `session` and `verification`. Volunteers sign in with an SMS one-time code and stay signed in. Organisation membership, roles, domain scopes and shift-level authority are ours, in our tables, where row-level security can reach them.

## Considered options

**Clerk and WorkOS were both real candidates**, and price was not what settled it. WorkOS AuthKit is free to a million monthly active users with organisations and RBAC included, which at sixty volunteers is free forever; Clerk's organisations story is the murkier one, with its free plan described as including a hundred organisations while B2B organisations auth is also listed as a hundred-dollar monthly add-on — an ambiguity that is itself a warning, given this ticket was opened partly to avoid discovering a primitive behind a paywall halfway through.

**What settled it is that ADR 0007 made the database the enforcement point for tenancy.** Every query is filtered by row-level security on `app.org_id`, so the value has to come from somewhere trustworthy. If a hosted provider owns organisation membership, that fact arrives as a claim in a token — a second source of truth that Postgres cannot join against. ADR 0004 then removes the thing that normally hides the problem: with no session expiry, **revocation is the entire security model**, and a membership claim in a long-lived token is exactly the fact that outlives its truth. A volunteer removed by the Coordinator would keep a valid claim until something forced a refresh, and nothing would. With Better Auth in the same database, membership is a row, the lookup is an indexed read, and removal takes effect on the next request.

A smaller argument points the same way: a hosted provider would hold sixty volunteers' names and mobile numbers under a vendor account whose ownership ADR 0006 deliberately left unresolved.

**Better Auth's organization plugin was considered and declined**, which goes further than this ticket's stated default of "provider for identity and membership, roles for us." Instance-scoped authority is why. Being **Lead of *this* shift** is not a role anybody holds; ADR 0001 has a shift copying its roster, so leadership is already an attribute of the copied roster row. No RBAC primitive in any library models that, and adopting one for membership while keeping roles in our own tables would recreate the two-sources-of-truth problem inside a single process instead of across a network.

## Consequences

**The cost of self-hosting is ours and it is not zero.** Rate limiting, one-time-code brute-force protection, revocation correctness and the breach surface are all now maintained rather than bought, with no SOC 2 report to hand a board that asks. Better Auth's phone-number plugin is also visibly less mature than its email-OTP sibling, with open issues on its API shape and on hooking in a custom code sender. WorkOS remains the fallback, and choosing it later would mean rewriting how `org_id` is derived — not the roles, which is the half that matters.

**An SMS code proves control of a number, not the identity of a person**, and the number is the identifier. One number maps to exactly one Volunteer, unique on its normalised E.164 form, enforced by the database. This is a **POC-scoped simplification made knowingly**: a mother and daughter sharing a number is a real case at this rescue, and it is deferred rather than denied. When it arrives, the unique index, a person-picker after the code, and a switch-volunteer action that re-credits the actor without a new code all change together. Until then the workaround needs no code — the second person is a roster-only Volunteer with no Account.

**That same mechanism carries minors.** Under-18 volunteers are Volunteers without Accounts: rosterable, present in attendance, holding no login and ticking nothing, with their work credited to the adult who recorded it — which is true rather than a fudge, because that adult is the one making the claim. Whether minors may hold accounts at go-live is a question for the rescue's board, along with shared numbers. Both are cheap to defer because **ADR 0006 runs the POC with no volunteer accounts at all**; everything here is a go-live decision governed by that ADR's tripwire.

**A Volunteer exists before an Account and after it.** The Coordinator creates a Volunteer from a name and a mobile number, and that record is immediately rosterable — necessary, because ADR 0001 has shifts copying their roster and somebody must be able to roster a person who has not onboarded and may never. An SMS invite opens login, the code verifies, and the Account is *claimed* rather than created. Care records reference the Volunteer, never the Account.

**Login SMS and notification SMS are separate senders with separate budgets and separate kill switches.** ADR 0004 caps outbound messages and gives them a server-side kill switch; if login shared that budget, a notification storm would lock the entire roster out of the app at the exact moment something was wrong. The separation also resolves a conflict the two ADRs would otherwise have had: ADR 0004 requires that opting out of SMS be honoured, and had login shared the sender, honouring an opt-out would have meant locking someone out. **Notification opt-out never affects login.** The inverse — a volunteer texting STOP to the auth sender — does lock them out, is not undoable by the app, and is recovered through the Coordinator, with the roster showing them unreachable per ADR 0004. If the Coordinator is the one locked out, the bootstrap command below is the floor.

**Email is a channel, not an identity.** ADR 0004 gives it the non-urgent half of messaging. It is optional at invite, because requiring it would block a Coordinator standing in a barn with a name and a phone number, and it is never a login factor or a recovery path.

**`app.org_id` is derived server-side on every request** — session to user to membership to `SET LOCAL`, inside the transaction the query runs in. Never from a URL, header or body: a client-supplied organisation id is the impersonation vector this whole arrangement exists to close. When a volunteer belongs to more than one rescue, the active organisation is a server-side session attribute changed by an explicit switch.

**The Board tablet is not a user.** It gets its own device-token path — organisation-scoped, read-only, individually revocable, listed in admin so you can see which tablet holds which token — resolved to an organisation the same way but hard-gated to read endpoints. A tablet left running in a barn is the least physically secure thing in this system, and if it held something shaped like a user session, the only thing preventing it from writing would be that nobody had wired up the button yet.

**Sessions are database rows, not tokens.** An httpOnly, Secure, SameSite=Lax cookie carries a session id against a long expiry refreshed on use; there are no JWTs anywhere, so revocation is a delete with no staleness window. `BETTER_AUTH_SECRET` lives in 1Password and is injected at deploy per ADR 0006, because a lost signing secret would sign out every volunteer at once and ADR 0004 made permanent sessions the point.

**A restore can resurrect a revoked session.** Sessions live in Postgres and Postgres restores from a dump up to fifteen minutes old, so a volunteer removed at 09:50 before a 09:55 failure comes back. Unlikely, and genuinely bad if it lands. Revocations therefore go in the audit log the brief already requires, and **re-applying revocations made since the dump is a line in the restore runbook** — the alternative is accepting it silently, which reads fine in an ADR and badly in an incident.

**The code endpoint is unauthenticated and spends real money.** Three sends per hour and five per day per number with backoff; a global auth-SMS cap separate from ADR 0004's notification cap, set high enough that onboarding sixty volunteers in a week never trips it, and which alerts rather than silently refusing. Codes are six digits, expire in five minutes, and are invalidated after five failed attempts. **An unrecognised number is told it is unrecognised**, deliberately against the usual "if that number is registered…" convention: enumerating a sixty-person invite-only roster is not a meaningful threat, and the conventional answer leaves a volunteer standing in a barn waiting for a code that a mistyped digit guaranteed would never arrive.

**No impersonation, and no god-mode.** ADR 0007 already built the diagnostic path — structured logs keyed by idempotency key answer the question "did the server ever see this write," which is what "it didn't save" actually means. The maintainer's elevated access is President or Board Member through the same role tables as everyone else, because a second privileged path is a second thing to secure and is reliably the one nobody audits. A one-shot CLI command creates the first organisation and its first member, run once, recorded in the runbook beside the restore.

**#9 inherits the roles, not the plumbing.** This decision fixes where roles live and what authentication is permitted to own. The domain scope list, how roles map to scopes, and how instance-scoped authority is represented are #9's to settle.
