# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

The skeleton exists, identity is on it, and **the roster is the first domain on top, horses and Spaces are the second** (#34, #35). Fifteen reads and thirty-five writes, a login screen, a home page, seven desktop admin screens under `src/routes/admin/`, three phone screens — `src/routes/horses/` and `src/routes/shifts.tsx` — and the tablet Board at `src/routes/board.tsx`. `mutation` dedupes — it opens the transaction, records the key inside it and hands the handler the scoped `db`, so a write's effect, its key and its audit entry commit together (ADR 0020). Every endpoint is declared in `src/shared/api-contract.ts`, which is where every new one goes: the server registers against that contract and the phone calls against it, so a path or an answer shape neither side agrees on does not compile (ADR 0021). The rest of "Domain model" below is still a description of what the code will model — shifts, checklists and reports land ticket by ticket.

**Signing in works, and it is where the shape of authorization is already settled** (#33). A Volunteer is created by a coordinator from a name and an email; they sign in with a six-digit code mailed to that address; the Account is _claimed_ rather than created, and nothing in the care record will ever reference it (ADR 0008, 0009). Sessions are rows in Postgres and revocation is a delete with no staleness window, because `src/server/request-context.ts` resolves the actor from the session on **every** request rather than trusting a token. Roles are rows; the role-to-Domain-Scope mapping is a constant — now in `src/shared/roles.ts`, because the admin screen grants Roles and shows what they carry, with the _checks_ still on the server in `src/server/api/authorization.ts` — and never a table (ADR 0010). There is **no impersonation and no god-mode** — the first President is made by `npm run bootstrap`, once, and holds `grants` through the same tables as everybody else.

**The three rostering gates are derived, never stored, and there is no override** (#34). `src/shared/rostering.ts` is a pure function of a Volunteer's facts and a day: an Orientation, a current Release, and for a minor a Consent. Two of the three go stale, and **both staleness rules are read-time derivations rather than a scheduled job** — an eighteenth birthday obsoletes a parent's signature and retires the Consent on the morning itself, and a Release Version published with the obsoletes flag stales every signature given before its valid-from. Nothing is ever auto-removed from a roster: a failing gate **flags** (ADR 0017), because a re-papering would otherwise empty every roster in the system on one morning. The date of birth is where the care goes — day and month are on the floor because the rescue has a party, the **year and the age sit behind `roster`** with contact details, and under-18 is shown as a state and never as a number. Redaction happens once, in `src/server/roster/people.ts`, on the way out.

Two things ADR 0017 asks for that #34 deliberately did **not** build, recorded so a later reader can tell deferred from forgotten. **The blank template a Release Version carries** — "one file per version, uploaded under `roster`" — is not stored: #32 puts document storage out of v1, and a URL column pointing at nothing would be worse than the column's absence. It lands with object storage, and `release_versions` takes one column when it does. **The gate is not armed.** ADR 0017 wants arming to be "one deliberate human act when the backfill is declared complete", and the backfill is sixty real dates read off paper by a person; nothing consumes rosterability yet, because Shifts do not exist, so there is nothing for an unarmed gate to fail open on. Arming belongs with the Shift roster, and it must not become a config flag that lingers.

**The audit log is derived and losable, and what lands in it is ADR 0003's tiers rather than taste.** Current-state edits get an entry; grants and revocations get one carrying actor, subject and reason; **publishing a Release Version gets none**, because a versioned-tier change _is_ a version. Denials stay structured logs, not rows. Reading the log is behind `roster`, one of ADR 0010's two carve-outs from the read-everything floor.

**Horses and Spaces are current state plus an audit entry, and a Space is one entity with a kind** (#35, ADR 0002, 0003). `src/server/horses/records.ts` is where a horse_care holder creates and edits both; `src/server/horses/list.ts` is where every Volunteer reads them, Departed horses included, because hiding one from a work surface is the phone list's job and never the read's — the profile at `/horses/$horseId` stays reachable so the history never goes with the horse leaving. A horse holds at most one Space per kind — stall, pasture, paddock, barn (#57) — as a row in `horse_space_assignments` rather than a column per kind, the way a Role is a row on `volunteer_roles` rather than a flag; splitting or merging a joined Space is an edit of its name and kind in place, never a new row. Alerts is a heading on the profile with nothing under it yet — ADR 0003's current-state list does not name it, and nothing in this ticket writes one, so the place is held rather than a field invented for a domain that does not exist. The horse photo is a URL column, not stored bytes: this application has no object storage yet, the same gap #34 left the release template pointing at.

**The Board is the third domain, and it is the first surface that is not a person** (#37, ADR 0022). `/board` answers the whole grid in one read — stalls in stall order with the OPEN stall's row kept, each barn that holds stall-less horses as its own section, and a horse the app cannot place still on the board rather than dropped. The ordering and the sectioning are a pure derivation in `src/shared/board.ts` (a stall's number is read out of its name, so `10` follows `9` and the joined `2 & 3` sits where stall 2 was); `src/server/board/grid.ts` reads the rows and leaves Departed horses off, which is the one place a read hides a horse and it is right because the Board _is_ the whiteboard. **The tablet authenticates as the barn**: one kiosk token in `BOARD_TOKEN`, presented as a header, resolving to no `Actor` — so nothing is credited — and `mutation` takes `PersonAuthorization`, so a write declaring `board()` does not compile. Colour on the screen comes from the Product's kind rather than from a pen somebody picked up, a blank says _no lunch feeding_ in words, and a failed poll leaves the last grid up with its age against it instead of blanking a wall people read across a barn.

**Shifts are the fifth domain, and the Shift is where the copy is the design** (#39, ADR 0001). A Shift Pattern is the recurring commitment — a weekday, a time of day and a type — and `/shifts/generation` fills a rolling two-week horizon from it, **copying** the Standing Roster, the start time and the headcount onto each dated Shift rather than resolving them later. That is what makes _who was supposed to be there on the 14th_ answerable after somebody edits the Pattern: an edit reaches the Shifts already standing **only when the caller says so**, and `applyToScheduled` is a required field on every editing endpoint rather than a default, because ADR 0001 is explicit that without the prompt the model is quietly wrong in the most common editing case. Generation is deliberate, never at boot, and safe to repeat — `src/shared/generation.ts` decides which occurrences are missing and the unique index on `(org_id, pattern_id, day)` holds when two runs overlap. **There is no `cancelled` and no state column**: a Shift nobody can staff is still a Shift, and `in_progress` is derived from the clock until Attendance can honestly write the transition.

**Cover and Drop are the volunteer's own, and neither queues.** A Drop **marks** the roster row — rostered-and-dropped is not never-rostered, and a removal by `roster` is a third state on the same row — carries an optional reason, and touches that Shift alone and never the Pattern behind it. A Cover lands immediately as a `volunteer`, never as a Lead, marked `origin: 'cover'`, and is **refused only for a missing Orientation**: a Shift needing medication still takes somebody who cannot give it. A Coordinator's hand placement on one Shift is a third origin, `assigned`, because it is neither a copy of a standing arrangement nor a Cover. Both Cover and Drop declare `neverQueued: true` in the contract, which is ADR 0011's carve-out from ADR 0005 as ADR 0018 restates it — _the app queues when it is the ledger and not when it is the medium_ — written where the phone's queue will read it rather than left for whoever builds it to remember. **The #34 gates are a hard block at both assignment doors** (a Standing Roster and a dated Shift) and at **neither** generation: an assignment that silently evaporated a fortnight later is the quiet wrongness the prompt exists to prevent, so a volunteer who has gone stale arrives on the Shift **flagged**, with their gaps on the roster row.

**Staffing is where a computed fact and a person's judgement are kept apart** (#40, ADR 0011). A **Staffing Gap** is derived — Unstaffed, no Lead, below Target Headcount, and nobody rostered holding Medication Authority on a Shift whose feeding includes a medication Product — across the whole two-week horizon, because a roster is built a fortnight out. `src/shared/staffing.ts` is the pure derivation and the one place the sentences are written, so the phone, the desk and the digest cannot describe Thursday differently; **Unstaffed is answered alone**, since four facts about an empty Shift is one fact spelled four times. The phrase _staffing gap_ reaches no screen. **Short is a person saying so** — actor and time on the Shift, no audit entry — and the app is on neither side of it: arithmetic never declares it, and a third volunteer Covering never withdraws it, because the human who declared it already weighed who might turn up. An Unstaffed Shift is never removed; it is the first thing in the digest.

**Shift Authority is armed, and it is the first authorization that is a join.** ADR 0010's second reason anybody may act was declared and unresolvable until Shifts existed. `authorize` settles being signed in and answers `over-the-shift-it-names`; `src/server/shifts/authority.ts` runs the roster join, and `mutation` runs it from the payload's `shiftId` before the handler — so no handler can forget it. Two more type invariants fall out and are listed with the rest in `src/server/api/route.ts`: a **read** cannot declare Shift Authority (`ReadAuthorization`, because a read has no payload to name a Shift in), and a **write** that does must accept a `shiftId` (`MutationAuthorization`). A position that ended carries nothing. `roster` is the other door, which is how officers reach a Shift they are not on. **Acting Lead is claimed explicitly** by any rostered volunteer on a leaderless Shift, suggested by Medication Authority then tenure, staying `acting_lead` in the record and conferring no Medication Authority — and it is `neverQueued` under ADR 0018's restated rule — _the app queues when it is the ledger and not when it is the medium_ — rather than as a fresh carve-out from ADR 0005, because two volunteers each believing they are in charge of Thursday is the Cover failure with a different noun. Short queues, because there the app is the ledger: a Shift needing more people is true in the barn whether or not the app knows. **The evening digest is the one thing the app sends about staffing**: `/shifts/digest`, under `roster`, to holders of `roster` and never to the sixty, covering tomorrow and the day after with Unstaffed and no-Lead first. It goes out even when nothing is missing — a message that stops arriving is indistinguishable from one that broke — carries no volunteer's name, and reports `sent` against `recipients` so a failed send is visible rather than assumed. Its trigger is deliberate, like generation and `/weather/readings`, because an in-process interval is a job that stops at the next restart and nobody notices for a fortnight.

**The checklist is where a Task and a Subject meet, and materialization is the pure function that decides which pairs get an Item** (#41, ADR 0013). A **Task** is catalogue data the rescue edits under `horse_care` — subject kind, Essential or Discretionary, per-Shift or per-day, whether it needs Medication Authority, an optional Condition gate, an optional Prep target, a nullable tolerance, the closing flag, instruction text — a fixed fence the rescue chooses among rather than invents past, the same discipline `createProduct` keeps around a Product (`src/server/checklist/records.ts`). A **Task Assignment** says which Shift Type normally does one Task for a horse, a Space, or the rescue — the `GROOM` column generalized, versioned like a Threshold and carrying the same three states from #38: assigned, deliberately none, or **not yet decided**, which is the absence of a row and still produces an Item, because ADR 0013 refuses to let an unanswered question read as no work (`src/server/checklist/assignments.ts`, `/admin/tasks`). **Feed and Medicate Items bypass Task Assignment entirely** — computed straight from a horse's current Feed Schedule lines by Product kind, so Medicate alone carries `requiresMedicationAuthority`. `src/shared/materialization.ts` is the pure derivation, exhaustively table-tested: given the day's Shifts, the catalogue, the current Task Assignments, the Feed lines and the day's Condition answers, it is deterministic and idempotent by construction — every Item carries a `materializationKey`, and the unique index behind it is what holds when two runs of `/items/materialization` overlap, the same pairing `shiftsToGenerate` and `shifts_occurrence` make for generation. **A Condition is finally evaluated against its own Shift's window rather than the day-wide stand-in #38 shipped** — `src/server/checklist/materialize.ts` calls `windowFor` per Shift, which is the Shift this application did not have yet when that stand-in was written. A per-Day Item carries no `shiftId` and belongs to the day, satisfiable by either Shift; a Pop-up materializes nothing, because it authors its own list. `/shifts/:shiftId` — the second parameterised path (ADR 0021) — is the checklist a Shift shows on opening, grouped per horse and per Space, with `materialized: false` the honest answer for a day nothing has fixed yet rather than an invented empty list. **This ticket reads the checklist and does not tick it**: no outcome — Done, Dropped, Not done — exists on an Item yet, so a Prep panel can name what a Shift is owed and cannot yet say whether it happened; that lands with the ticket that adds ADR 0013's four outcomes.

**The shift prep queue is where a tick becomes an offline-safe write, and Done is the one outcome it writes** (#42, ADR 0005, ADR 0013, ADR 0020). `item_outcomes` is the append-only series ADR 0013 describes — one row per claim, `outcome` text rather than an enum so Dropped and Not done arrive as a value rather than a migration, current outcome the latest row rather than a column overwritten in place — and `/items/done` (`src/server/checklist/tick.ts`) is the one write this ticket gives it: any Volunteer rostered on the Shift named may tick any Item that Shift shows, on `floor('work-on-a-shift-you-are-rostered-on')` rather than Shift Authority, which #34's own floor already refused as a third axis past ADR 0010's two; Medicate needs Medication Authority besides, checked and refused explicitly rather than hidden, and every claim credits the actor who made it — the Board has no write door at all to credit instead (ADR 0022). `shiftId` names the Shift open on the phone rather than the Item's own, which is what lets a per-Day Item be ticked from either Shift that shares its day. **`src/shared/tick-queue.ts`'s `TickQueue` is the retry queue ADR 0005 describes**, its store injectable and defaulted to the real one — `src/shared/tick-store.browser.ts`'s IndexedDB, falling back to an in-memory store on a browser with none, which is also the whole of what the queue's own test needs — the same shape `idempotency`, `context` and `shiftAuthority` already take in `route.ts`. A tick keeps its minted key across every retry, and what a caught error means is decided once, there, rather than at every tap: an `OutdatedServerError` waits, an `OutdatedClientError` waits and surfaces a reload banner, and any other `ApiError` is ADR 0020's _a repeat gets the first response_ read the other way — retrying under that key can only replay the same refusal, so the claim is denied and dropped rather than held forever. The Work Surface at `/shifts/$shiftId` renders `src/shared/prep-queue.ts`'s arrangement — per-horse cards in stall order (`compareStallNames`, reused from the Board), per-Space Items grouped after — and a card's checkbox reads Unsent from the queue and Done only from a `/shifts/:shiftId` re-read after the queue settles, so nothing looks Done the server has not confirmed and nothing it confirmed still reads Unsent. **Dropped and Not done are not built**; `outcome` is ready for them, and they are a later ticket's write, the same kind of deferral ADR 0013 names for close and for reopen.

**The installable shell is the PWA half of ADR 0004, and the service worker caches the shell only** (#48). `public/manifest.webmanifest` names the icon and the `standalone` display that turn Add to Home Screen into an icon opening into the Work Surface, and `src/routes/__root.tsx`'s `head` links it alongside a theme colour; installing stays optional and nothing anywhere gates on it, so signing in and the Board both work exactly as they do in a plain, uninstalled tab. `public/sw.js` is a **static** worker script — served as-is, never a bundle input — with two strategies and nothing past them: a navigation is network-first, so an online reload always answers with what the server just rendered, and an offline one answers from whatever was last cached under that same URL instead of the browser's own error page; `/assets/`, Vite's content-hashed build output, is cache-first, because the bytes at a given hash never change. **`/api/` is never touched at all** — not cached, not intercepted, not even passed through `respondWith` — so a network failure surfaces to `src/shared/api-client.ts` exactly as it would with no worker installed, and the retry queue (#42) stays the only thing with an opinion about a write's durability. The update strategy is `self.skipWaiting()` and `self.clients.claim()` on every install, safe only because navigation is network-first — the next page a volunteer opens already asks the network for fresh HTML and fresh asset hashes — and `CACHE_NAME` carries a hand-bumped version that `activate` uses to purge every cache under the one before it, which is what keeps a stuck-forever shell from being possible rather than merely unlikely. `src/shared/service-worker.browser.ts`'s `registerServiceWorker` is the one line `src/client.tsx` calls alongside `startObservability`, twinned with `src/shared/tick-store.browser.ts` in shape: a no-op wherever `navigator.serviceWorker` does not exist, so an old browser gets the plain responsive app rather than a thrown error.

**Attendance is the sign-in sheet, replaced, and a departure is never invented** (#43, ADR 0012). A per-visit `attendance` row carries an arrival, an optional departure, an optional Shift and — for a Visit, the case with no Shift — a job in the volunteer's own words plus a coarse category, which `src/server/attendance/records.ts`'s `signIn` fixes to `shift` on a Shift row regardless of what a caller sends and requires as one of the rest on a Visit. **Anyone may record anyone's arrival or departure, in both directions**, on the floor and attributed to whoever asked rather than to the person named — `floor('record-your-own-presence')` in `src/server/api/authorization.ts` covers both, on ADR 0012's own reading of "your own." `signOut` **resolves** the open row from the Volunteer and, where one applies, the Shift, rather than taking an Attendance id — which is what lets a plain Volunteer close their own Visit without first reading a ledger that sits behind `roster`. Nothing here ever writes a departure but a person: there is no clock, no job, no scheduled close. The fourth roster fact ADR 0012 adds to ADR 0011's three — _rostered, absent, no Drop_ — is `rosteredAbsent` in `src/shared/attendance.ts`, computed from the minimal arrival/departure pairs `src/server/shifts/list.ts` folds into the already floor-readable `/shifts`, displayed and never interpreted. The **whole** ledger — who recorded what, a Visit's description, the Supervising Adult and their phone number — is `/attendance`, put behind `roster` for the desktop hours report this ticket's acceptance asks for, a narrower gate than ADR 0012's own argument for the read-everything floor and recorded here as the deliberate departure it is. Per-county hours at `/admin/attendance` are two pure renderings of that same ledger in `src/shared/attendance.ts` — Calvert's one row per visit, flagged and never truncated past its eight-hour cap; Anne Arundel's dates and a total — because rows compose upward into totals and totals never decompose back into rows.

**Observations and Escalations are the Facebook group's reporting job, without the scroll** (#44, ADR 0014). An **Observation** is free text with an optional subject — a horse, a Space, a Product, or a record that is wrong, named by `subjectLabel` at write time rather than resolved from a join later — recorded by whoever noticed and needing no Domain Scope: `floor('record-an-observation')` in `src/server/api/authorization.ts`. It attaches to the **recorder's own** Attendance, resolved the way `signOut` resolves one, and is never edited or deleted once it lands — there is no `/observations/edit` in the contract, and nothing in `src/server/observations/records.ts` writes its text a second time. **Shift Authority may record on a rostered volunteer's behalf**, naming them as `observedBy` apart from `recordedBy` — "recorded by Kate, observed by Joy" — checked inside `recordObservation` rather than declared on the route, because a nullable `shiftId` means this write can never be typed as Shift Authority's own (ADR 0016's `MutationAuthorization`). An **Escalation** is a separate record, carrying the escalator's own framing and addressed to exactly one Domain Scope: Shift Authority over the Observation's own Shift, or a holder of that Scope adopting it into their own, both resolved inside `src/server/observations/escalations.ts` on `claimActingLead`'s own precedent for a check too data-dependent to be a static declaration. **One Observation may carry many Escalations, and they share no state** — closing one never touches another. Delivery mails the Scope's current holders through `src/server/email.ts`, the same sender `requestCode` uses, resolved via `peopleList` against real grants rather than a cached list; closing needs a holder of the addressed Scope and a note, and mails the reporter the note in full; the thread at `/escalations/comments` is floor-writable, before close and after — ADR 0010's fourth scope-free write. **On a Visit there is no Lead**, so the volunteer dispositions their own Observations at sign-out — Escalate, adopting into a held Scope, or noted with no action at `/observations/note` — and `signOut` in `src/server/attendance/records.ts` now refuses to close a Visit carrying an undispositioned one. Coalescing delivery over ten minutes, the Shift-close gate for a Shift's own Observations, and the browsable Reports screen's full curation are #45's and later work's, noted rather than built.

**Supplies is where the whiteboard finally does the arithmetic, and the Reorder is the third table that did not become an event store built by accident** (#47, ADR 0019). A **Days-of-Supply reading** is ADR 0003's measurement-series tier at its plainest — a date, an actor and a number of days against one Product, appended to `days_of_supply_readings` and never edited — and the app's only addition is time: `src/shared/supplies.ts`'s `projectedDaysRemaining` subtracts the days elapsed in the organisation's own calendar and floors at zero, so 14.5 written on the 4th reads 9.5 on the 9th and never a negative number the app does not actually know. `isAtOrBelowReorderPoint` is the one fact `supplies` holders are shown, never mailed — the digest section ADR 0019 also describes stays unbuilt here, the same way #34 left the gate unarmed, because nothing yet reads a crossing on a schedule. **Nothing here divides a sack**: the derivation reads only `days_of_supply_readings`, never a Feed Schedule line, because `amount` is free text and "2 wells" answers no arithmetic question. **Readings are written by holders of `supplies`, or by whoever presently carries Shift Authority** — the same data-dependent OR `escalateObservation` established above, resolved inside `src/server/supplies/records.ts` rather than declared on the route, because an optional `shiftId` means `/supplies/readings` can never be typed as Shift Authority's own. **A Reorder borrows the Escalation's shape rather than becoming a fourth hand-rolled log**: Open until a `supplies` holder closes it with a note, carrying an append-only thread (`reorders`, `reorder_comments`) that, unlike the Escalation's, is writable by `supplies` holders alone — a Reorder has no reporter with standing, and the linked Escalation is where the floor still has a voice. `escalationId` links back and shares no state: closing the Reorder never touches the Escalation it was created from, and closing that Escalation never advances the Reorder. `src/routes/supplies.tsx` is the one new phone screen, readable by everyone, offering the reading form only to whoever the server will actually take it from. **A Product the rescue stops using is Retired, not deleted** (#64): `products.retired_on` is a nullable date set through `/products/retirement` by the same two Scopes that edit one, current state with an audit entry, the third instance of an act a Space and a horse already had. `horsesByProductOnCurrentSchedules` in `src/server/horses/feed-schedules.ts` is the one place _in use_ is decided — a **current** version, for a horse that has **not Departed** — and both seams read it: `retireProduct` refuses `product_in_use` against it, and `/products` carries `onFeedSchedules` counted from it, so the desk reads _on 9 horses' Feed Schedules_ and disables the button before the refusal it would otherwise hit. The block is two-sided, because a one-sided one leaks the next morning: a Retired Product is named on no new Feed Schedule version, no new reading and no new Reorder (`product_retired`), while a Reorder already Open threads and closes normally. The reads disagree deliberately — `/products` carries it marked, `/supplies` drops it, every picker hides it, a Whiteboard Read still skips it as already-held and says _retired_ in the report — and `materializeDay` is untouched, because a horse not fed is worse than a stale catalogue row.

**Closing is where the record becomes true, and a closed Shift never reopens** (#45, ADR 0013, ADR 0014). `item_outcomes` gains the two outcomes #42 left as a value rather than a migration — `/items/drop` (`src/server/checklist/tick.ts`'s `dropItem`) needs Shift Authority and is refused once **past tolerance**, and `/items/not-done` sits on the same floor `/items/done` does, because a deviation from the materialized plan — "it warmed up and we did not blanket" — is recorded by whoever is standing on the Shift, the plan itself never changing mid-Shift. **A skip is any outcome that is not Done, blanks included**: `src/shared/item-outcomes.ts`'s `consecutiveSkips` and `isOverdue` are the one pure test both the write and the checklist card read, so Drop is withdrawn on the same Item the screen already marked overdue. **Assignment is a hint, never a gate** — `items.assignedToVolunteerId` is mutable and unaudited, set by self-claim or by Shift Authority naming somebody else rostered, through `/items/assign`. `src/shared/shift-close.ts`'s `closeBlockers` is the one function both seams read: the server's own two counts — an Open Attendance, an undispositioned Observation — plus the phone's own Unsent queue length (`TickQueue.pendingCount`), so the close button and `/shifts/close`'s refusal cannot disagree about what is blocking. `src/server/shifts/close.ts` is where a Shift becomes immutable domain fact: `shifts.closed_at`/`closed_by` are current-state and never cleared, and **an unmet Prep owed to this Shift Type is filed Not done, credited to whoever closed, and sent to nobody** — a visible record in the vocabulary that already exists rather than a fifth email. A late claim — Done, Dropped or Not done recorded after its Shift closed — is accepted and marked `late` on `item_outcomes`, because rejecting it would throw away work that actually happened; the close record itself stays the truthful snapshot it was at the moment of close. **Dispositions are Shift Authority's own act at close, not only the recorder's**: `/observations/disposition` (`src/server/observations/records.ts`'s `dispositionShiftObservation`) gives a Shift's own Observations the third exit ADR 0014 named and #44 deferred — curated into Shift Notes, which also appends the note itself — beside `noted_no_action`, both distinct from the Visit's own `/observations/note`. **Shift Notes** (`shift_notes`, `src/server/shifts/notes.ts`) are an appended list, never one field a second Lead's edit would silently erase, read by **date rather than by a pointer to a previous Shift** — recency is what lets Lunch and PM both see the morning's note without either being told it is the other's successor — and curated by Shift Authority while the Shift stands, by `horse_care` after it closes (ADR 0010's amendment: `shiftAuthority(['horse_care'])` on the route, `postClose` decided inside `addShiftNote` from the one fact the route's own join cannot see). **The Attestation is refused from a relative**: `attendance.attestation_relationship` is stored beside the Supervising Adult captured at sign-out, and `signOut` refuses anything but `none` — MSDE's own rule, that a parent, a guardian or a relative may not attest for a minor's service learning.

**Weather is the fourth domain, and it is where a number is a version and a question stays a question** (#38, ADR 0015). A **Threshold** is a rescue-wide default with per-horse overrides — versioned like a Feed Schedule and, for the same reason, with no audit entry — and it is **three-valued per horse**: overridden, deliberately the same as the default, or _not yet decided_, which is the **absence of a row** rather than a value, so a new intake is an unanswered question and not a horse that agreed to something. An undecided horse still gets its sheet at 38°, off the default, and `/admin/thresholds` says the decision is owed. Every row carries the **metric and the provider it was calibrated against**, because cold is air temperature and heat is real feel and two providers' real feel differ by up to ten degrees at the same coordinates (#6) — a swap without the stamp re-calibrates every horse in the barn and nobody notices.

**Condition evaluation is pure, and the window belongs to the Condition.** `src/shared/weather.ts` is the closed vocabulary — three predicate kinds, five Conditions, and a fourth of either is a deploy — and `src/shared/conditions.ts` resolves them **per subject**: _Staying In_ is one answer for the barn, _Sheet Weather_ is one per horse. Sheet and Blanket are mutually exclusive **by construction**, because the coldest hour of the window decides: a night that touches 25° and 45° dresses the horse for 25° and generates one garment rather than two for a volunteer to choose between. Day-scoped Conditions read the whole day; shift-scoped ones read from a Shift's start until the next begins, which `windowFor` implements and the table tests cover, though nothing passes it a Shift yet because Shifts do not exist. A Condition the forecast could not answer is **`holds: null` with a reason**, never false — defaulting to false on a 90° day is horses going out and getting the normal hay.

**A Reading is kept whole, and `src/server/weather/providers.ts` is the only module that knows a URL.** Open-Meteo is primary and `api.weather.gov` is the fallback — which #38 asks for and ADR 0015 deferred, and the ADR's objection is answered rather than ignored: the fallback carries **no apparent temperature at all**, so a fallback Reading resolves the cold rules and leaves the heat rule unresolved instead of answering it on a scale the barn's 85 was never set against, and the Reading records who answered and who did not. Nobody answering reuses the day's last Reading marked stale (ADR 0015's step one) and otherwise refuses; the hand-resolution step is Shift Authority's and lands with Shifts. `/weather/readings` is the act that fixes a day, under `horse_care`, and becomes the daily job's first step the day there is a daily job. The barn's coordinates are `BARN_LATITUDE` and `BARN_LONGITUDE` — configuration, like the kiosk token, because nothing in the app edits where the barn is — and unset fails closed.

**Two prefactors ADR 0021 named and left undone landed with the horse profile, because it is the first endpoint that needed them.** `PathParamNames`/`PathParams` in `src/shared/api-contract.ts` extract a path's `:name` segments as a type, and `ApiClient.get` takes them as a second argument and interpolates them — `/horses/:horseId` is the first parameterised path, and a caller who omits the param or misnames it fails to compile. And the UI component-test seam is real: `src/test/route-harness.tsx` renders a real route component inside a real router, `src/test/api-stub.ts` stubs `fetch` at the network boundary so the real typed client and contract parsing run, and `vitest.config.ts` splits into a `node` project and a `jsdom` one so `.test.tsx` files get a DOM without paying for one everywhere else.

**Announcements are the wall, and Contacts are the phone numbers beside it** (#46, ADR 0018). Any Domain Scope holder posts an Announcement — text, author and a mandatory expiry the writer sets, and no subject field exists on either the read or the write, because anything about one horse already has a better home. `anyScopeHolder` in `src/server/api/authorization.ts` is the new check shape ADR 0018 asks for — holding _any_ Domain Scope, unnamed, rather than an enumerated pair — and it is what both posting and editing declare: ADR 0010 has no authorship axis for "the author may also edit" to lean on, so any Scope holder is the whole of the check. It carries **no audit entry**, the way a Release Version carries none, because the only reader of who changed a wall notice is somebody standing at the wall. `src/shared/announcements.ts` is the pure, table-tested derivation of what still counts as posted on a given day; `src/server/announcements/list.ts` reads it once for the two surfaces that show it — the home screen, only when there is something to show (`src/routes/index.tsx`), and the Board (`src/server/board/grid.ts`, `src/routes/board.tsx`), which is where ADR 0018 says the whiteboard's missing Reminders panel finally lands. **It is never sent anywhere**: both `/announcements` writes declare `neverQueued: true`, ADR 0018's restated carve-out from ADR 0005 — the app is the medium here and not the ledger, the same shape as Cover and Drop. Contacts is the read-only screen everybody reads, at `src/routes/contacts.tsx` — posted numbers with their hours and what they are for, plus the rescue's standing rules, the residue of the board's Reminders panel once the rest of it decomposed into existing models — maintained under `roster` at `src/routes/admin/contacts.tsx` (`src/server/contacts/records.ts`, `src/server/contacts/list.ts`) and resolved to by nothing: neither `contacts` nor `standing_rules` carries a field an Escalation could ever point at.

**Pasture, Paddock and Topical are three words the vocabulary was missing, and each one changes a derivation** (#57, #58, ADR 0002's amendment). `SPACE_KINDS` **renames** `field` to `pasture` and adds `paddock` rather than keeping four values around one dead one: a Paddock is a smaller enclosure attached to a Pasture, a horse turned out is in both at once, and one kind could never say that while a horse holds at most one Space per kind. `0018_a_pasture_and_a_paddock` rewrites `spaces.kind` and `horse_space_assignments.kind` together, because the assignment row carries its own copy of the kind and the primary key would otherwise disagree with the join; `isSpaceKind` and the contract's `spaceKind` follow from the constant, so `/horses/space` moved for free (ADR 0021), and the lettered-versus-numbered rule became `LETTERED_KINDS` because the amendment made it two. `PRODUCT_KINDS` gains **`topical`** — zinc oxide, sunblock, fly spray, what goes _on_ a horse rather than in it — a Product so Days of Supply can count fly spray and deliberately **not** a `medication`, since a Medicate Item carries `requiresMedicationAuthority` and only a holder of it could then fly-spray a horse. The bite is in `materializeDay`: the split was `productKind !== 'medication'` → feeding, so a fourth kind joined the Feed Item in silence and a horse was told to eat fly spray. It is now `ITEM_FOR_PRODUCT_KIND` in `src/shared/products.ts`, a total `Record` so a fifth kind does not compile until somebody decides which of the three answers it takes — and a stored kind this build cannot name generates **nothing** rather than being guessed into the feeding. A Topical generates no Item at all: the work is a Task carrying an instruction, which is where fly spray and sunscreen already live (ADR 0013).

**The Whiteboard Read is the one place this application writes without a human confirming each record, and ADR 0023 is where that is argued** (#59). `POST /whiteboard-read` takes a declared `panel` and a base64 image and answers **the report, not a table** — created, skipped-as-already-held, left-blank, could-not-place, plus every created `medication` named for a `horse_care` holder to check, because `prescription` is required on `/products` and no board says it. **The human says which panel it is** before shooting, from a dropdown at `/admin/whiteboard-read`: barns structure their boards differently and a misclassified panel writes to the wrong tables. `src/server/whiteboard-read/model.ts` is **the only module that knows the model API**, the shape `src/server/weather/providers.ts` holds for the forecast — `claude-sonnet-5` **through OpenRouter**, key in `OPENROUTER_API_KEY`, unset failing closed in words — and `setWhiteboardReader` is the seam `setEmailTransport` already is, so nothing in the test suite makes a paid call. #59 named the Anthropic API directly and the rescue overruled it: one gateway subscription already paid for beats a second account nobody else can see, OpenRouter serves Anthropic's own Messages shape at `/api/v1/messages`, so this is a base URL and a key name rather than a second dialect — and the reading arrives as a **forced tool call** rather than through `output_config.format`, because tool use is the one JSON-shaping mechanism a gateway proxies faithfully for every model behind it. **Authorization is the Scopes the panel writes into and no new axis** (ADR 0010): `RECORD_SCOPE` and `PANEL_RECORDS` in `src/shared/whiteboard.ts` derive `scopesForPanel`, the route declares the looser `anyDomainScope(['horse_care', 'roster'])` and the real check runs inside `recordWhiteboardRead` — the data-dependent shape `escalateObservation` and `recordSuppliesReading` already resolve inside themselves — so a caller holding `roster` is refused the grid. **Three rules stand in for the review step.** Nothing is confidence-scored and an illegible cell is left **blank** and named. It is **additive only** — a name already held is skipped and named back as `/spaces/batch` does, and a horse already held is skipped _whole_, feed lines and all, so a second run cannot overwrite a correction. And **partial writes are the point**: what the model returns is parsed **per element** against `src/shared/whiteboard.ts`'s strict schemas — built from the same four constants the contract builds `spaceKind`, `productKind`, `shiftType` and `route` from — so nine horses read out of ten writes nine and reports the tenth. It writes through the same `createSpaces`, `createHorse`, `createProduct`, `publishFeedSchedule`, `createContact` and `createStandingRule` the desk screens call, so the durable trail is **one audit entry per created record** carrying the caller and the reason _read from the whiteboard photograph_ — no import log, which is the fifth hand-rolled table ADR 0019 warned about. The image is **never stored**, and the write declares `neverQueued: true` while keeping its key: a desk act done once on wifi, and holding five megabytes in IndexedDB to retry would buy nothing and cost a second paid call (ADR 0018). The ALERT column, Task Assignments, Announcements and Suppliers are all deliberately unread, each for a reason the ticket records.

**An Alert is standing, scoped to `horse_care`, and reaches all three surfaces in full words** (#60, ADR 0024). `alerts` is ADR 0003's current-state tier with an audit entry — a fourth member beside name, halter colour and Space assignments — and `ALERT_KINDS` in `src/shared/alerts.ts` is a closed fence of three: a prohibition, a care alert, an allergy, and a fourth is a deploy. **The subject is a horse and nothing else**; a standing warning about a Space is a maintenance Escalation, which already routes and already closes. **`horse_care` raises, edits and ends, and nobody else** — a deliberate narrowing of ADR 0014, because an Alert anybody may post is a wall nobody reads and it is permanent where a Saturday's delay is not; the floor's own door is the Observation, which escalates and mails the Scope's holders. **Ending is a marker, an actor and a required reason** (`src/server/horses/alerts.ts`), never a delete and never an un-ending: the audit entry answers who and when, and only the reason answers _why the biting Alert is gone_. Nothing ends on its own — no review date, no scheduled job — and **a horse departing ends nothing**, because she is gone rather than cured. **There is no new read**: Alerts ride on `/horses/:horseId`, `/shifts/:shiftId` and `/board`, each gaining an `alerts` array, because a second call the Board polls alongside the grid would leave a horse looking alert-free whenever it is slow (#36). The `/horses` directory deliberately carries none — its screen shows no warning, and a promise nothing reads is a promise that goes stale unwitnessed. The Board's long-held column renders the **full text rather than a count** — _2 alerts_ on a wall read across a barn tells nobody the horse bites — and `compareAlerts` is the one pure ordering all three surfaces read, so the wall and the phone cannot disagree about which warning comes first. Ended ones appear in a section on the horse profile alone, on the read-everything floor. The desk is `/admin/horses`; the whiteboard read (#59) still does not read the `ALERT` column, because the model would have to guess the kind and a mis-kinded safety fact is worse than the blank ADR 0023's first rule already prescribes.

**Navigation is a Sidebar, Home is the barn's dashboard, and a Volunteer may finally change something about themselves** (#66–#68, ADR 0026, ADR 0027). `src/shared/navigation.ts` is one hand-declared entry per Destination — path, label, group, Scopes — and a Destination is gated on **the write it exists to perform**, never its read: eleven of the twelve desk screens read through `readEverything`, so gating on the read would hide two and leave the rest dead in front of a plain Volunteer, who is now offered **General** and no **Admin** heading at all rather than an Admin heading with two entries under it. That overturns ADR 0011's disabled-and-explained rule for _Destinations_ and keeps it for _controls_ — a button on a screen you are on is still shown and refused. It is **cosmetic and never a boundary**: nothing in `src/server/` imports it, every path still works typed in, and the server still refuses. `navigation.test.ts` reads the route files off disk and asserts the table covers every one, so a screen added without an entry fails the build. The shell (`src/routes/__root.tsx`, `src/components/navigation.tsx`) is a shadcn Sidebar above 900px and a drawer below it; the bottom tab bar **stays** on the phone — one tap, thumb height, gloves and sunlight — and its five entries are all on the floor, so its shape never changes. **A visitor with no session gets no chrome at all** — the third bare case beside `/login` and `/board` — because the floor answer, the General group, is a menu of entries somebody with no session cannot open; a request that merely _did not arrive_ is the opposite case and keeps the navigation at its floor, since a volunteer whose signal dropped must not also lose the way back to Shifts. The footer carries the account: your name, the Theme menu moved out of the app bar, _Edit your details_, and Sign out, which had to leave Home first.

**Home stops being the menu.** `GET /home` (`src/server/home/page.ts`) composes four sections — your next Shift, the unexpired Announcements, Shifts needing cover **that you could actually cover**, and your open Escalations — in one read, on `/board`'s own precedent: every one is derivable from floor reads the phone already has, and composing on the client is exactly the half-loaded screen #60 refused. **Every section vanishes when it is empty**, ADR 0018's Announcement rule applied to all four, and all four empty gets one sentence rather than four blank headings. Nothing there is a new derivation: `mayCover` is the one Cover gate (an Orientation, never `rosterable` — a lapsed Release must not hide work from somebody offering to come), `PROMINENT_DAYS` moved into `src/shared/staffing.ts` so the dashboard and the Shifts screen shout at the same distance, and the four gaps travel as gaps so `staffingFact` stays the only place those sentences are written. A closed Shift is dropped from both the next-shift card and the cover list, which is the one thing `/shifts` itself still does not carry.

**Editing your own details is a floor, and the email is the credential.** `floor('edit-your-own-contact-details')` joins `record-your-own-presence` rather than becoming ADR 0010's forbidden third axis, and the subject-is-the-actor check is **structural**: `/me/contact-details` names no `volunteerId`, so there is no shape in which it reaches somebody else. Three fields and no more — name, mobile, email — because everything else about a Volunteer is a statement somebody else has to make, and a Release is already never self-recorded for exactly that reason (ADR 0017). Audited like any current-state edit and with **no `reason`**, since a reason exists to explain a decision about another person. Name and mobile commit at once. The email does not: `requestCode` gates on `volunteers.email`, so moving it naively is a permanent lockout only a Coordinator can undo. `/me/email/code` mints a **`change-email`** OTP — a different type from `sign-in`, so the code is structurally unreachable from the login screen — and sends it itself, because Better Auth's own sender swallows failures. `/me/email` verifies it in `src/server/auth/email-change.ts`, then moves `volunteers.email` and `user.email` **in one transaction**: Better Auth's adapter holds `rawDb()` and can never join `mutation`'s, so `user` — which carries no `org_id` and no policy — is written directly here, the one deliberate exception to `revoke.ts`'s rule against a second writer. Verification is ours because `checkVerificationOTP` refuses any address with no `user` row, which is every new address; `storeOTP` is now `{ hash: hashCode }`, identical to the library's own and owned here so the verify is not a reimplementation of an internal. Afterwards every other session is deleted, and the old address is told — logged rather than thrown, because refusing a completed credential change over an undeliverable notice leaves somebody with an address they cannot sign in at. **`roster` has no door of its own to these three yet**, which ADR 0027 assumes and no ticket has built.

**A horse's Timeline is the Facebook group's other job, and it is a read and nothing else** (#74). `src/server/horses/timeline.ts` composes what the app already held across four screens — Observations naming the horse with the Escalations they became **underneath** them rather than beside them, Alerts raised and ended both, every measurement, and every Feed Schedule version — and carries it on `/horses/:horseId`, on `/board`'s and `/home`'s own precedent: a second call fired alongside the rest leaves the horse looking eventless whenever it is slow. Every entry is ordered by when it was **recorded**, never by the date it is about — a weight taken on the 1st and written down on the 5th sits on the 5th with `takenOn` beside it — and `src/shared/timeline.ts` is that one rule for five kinds, with an id tiebreak so two reads of one horse cannot disagree. The day a person reads is resolved by the server in the organisation's timezone (ADR 0007, ADR 0016). The rescue-wide half rides on `/horses` as a **second tab**: a horse is on it because she has an open Escalation or a standing Alert, with the newest sentence against her name, **derived on every read** — no `has_issues` column, no `watching` table — so closing the one or ending the other drops her out with nothing to clear. A **Departed horse leaves the list and keeps her Timeline whole**, because the history must not go with the horse leaving (#35), and the directory rows still carry no Alerts: #60 decided that deliberately, and _horses with something going on_ is a different promise from a warning beside sixty names. `observations_subject` is the one schema change — `subject_kind` and `subject_id` are the pair a subject is, since an Observation names a Space or _a record that is wrong_ as readily as a horse.

**`/` answers a visitor with a page rather than a login form, because a carrier reads it** (#75, ADR 0028). 10DLC campaign vetting wants to see what the messages are and how the people receiving them consented; `src/components/landing.tsx` says both, plus what Caballus is, who runs it, that there is no public sign-up, and that STOP stops the texts and never the sign-in. It is `/`'s `signed-out` branch and nothing else changes — #66 already made a visitor with no session the third bare case, so there is no chrome to remove and a signed-in volunteer never sees it. It lives in `src/components/` and **not** in `src/routes/`, because a file there is a Destination the sidebar has to offer unless `navigation.test.ts` names it as an exclusion, and a marketing page in a volunteer's navigation is wrong on its face. The operator named is the maintainer personally, matching the Sole Proprietor brand ADR 0028 registers, with the ADR's tripwire recorded in the file.

**The privacy policy and the terms are two more pages a carrier reads, and they are routes because a campaign form takes a URL** (#80, ADR 0028). `/privacy` and `/terms` carry what vetting requires by name — the carrier's own non-sharing sentence about mobile numbers quoted rather than paraphrased, the message frequency and the app's own 120-a-day cap, _message and data rates may apply_, HELP, STOP, and that carriers are not liable for an undelivered message — and `privacy.test.tsx` and `terms.test.tsx` assert each of those **by its words**, because a rewording that drops one fails a campaign review a fortnight later in an email nobody reading a diff would connect back to it. `NO_SHARING` and `RATES` live in `src/components/public.tsx` beside the maintainer's address and the last-updated date, which is a hand-edited string rather than a rendered `new Date()` — a policy that says _today_ forever is the one thing a policy's date must never do. They are the **first route files that are not Destinations**, so `src/shared/navigation.test.ts` gains a fifth named exclusion beside `/login` and `src/routes/__root.tsx` a third and fourth bare path: a sidebar of twenty entries drawn around a privacy policy is chrome for a reviewer who has no session and cannot open one of them. The three public pages cross-link at the foot, because a reviewer lands on whichever URL was typed into the form.

**The Urgent Send is a send and not a noun, and it carries exactly two cases** (#77, ADR 0028). `src/server/sms.ts` is the one door out in the shape `src/server/email.ts` already holds — an injectable transport, a kill switch, a refusal rather than a silent drop, and a **daily cap of 120**, two full sends to sixty people. There is no Message, no Broadcast and no Notification table: what is stored is `urgent_sent_at`/`urgent_sent_by` on the `shifts` or `announcements` row that already exists. **It is a second, deliberate act** rather than a field on the write it follows, and the split is the design — declaring Short _queues_, because a Shift needing people is true in the barn whether or not the app knows, and a text does **not**, because one about Tuesday arriving on Thursday is the app as medium failing (ADR 0018). That is also the amendment to ADR 0018: posting an Announcement still sends nothing, and a second act may put one in front of people, once. **A gap is visible before the send** — `/reach` answers _this reaches 47 of 60_, from the same `isReachable` the fan-out walks, on the read-everything floor because it answers counts and never a number (and because a read cannot declare Shift Authority, which whoever may send a Short text might be holding alone). A Short text goes to whoever could **cover** it — `mayCover`, minus the people already standing on it — and never to the roster already coming. **SMS Consent is required at invite rather than optional**, because a field the form could leave out is a field it will leave out; **STOP is the carrier's record and the app keeps a copy**, stamped from Twilio's own 21610 the first time a send is refused for it, so there is no inbound webhook and the next count is still right.

**SMS is a second door into the app, and `/me/mobile` ships with it or none of it does** (#78, ADR 0029). The login screen takes an email address **or** a mobile number in one field — `looksLikeMobile` is shared, so the screen and the server cannot disagree about which was meant — and `src/server/auth/verify.ts` is Twilio **Verify**, which sits outside A2P registration entirely: no carrier queue in front of anybody being able to use the app, and a STOP on the notification campaign structurally cannot touch login. Verify proves the handset; the **session** is then minted through the one path that already claims an Account, a sign-in OTP for the Volunteer's own address created and consumed without being sent, so a text sign-in lands on the same `user` row and the same year-long session as a mailed one. `volunteers.mobile` is a **credential** now: stored in one spelling by `src/shared/mobile.ts`, and `volunteers_mobile_in_org` is the twin of the address index. So the mobile **left `/me/contact-details`** — which is name-only — for `/me/mobile/code` and `/me/mobile`, the shape ADR 0027 built for the address, against **two Verify Services** so a change-flow code cannot be checked at the login door. `/me/mobile/removal` needs no code: verification exists to stop somebody being locked out by a number they cannot receive at, and giving one up cannot lock anybody out. The notice to the old number is the one thing this application texts that is not an Urgent Send — addressed to one person about their own credential — and a failure there is logged rather than thrown, because refusing a completed credential change over an undeliverable notice leaves somebody with a number they cannot sign in at. **The brand and the campaign are paperwork (#76) and are not in this repository**; `docs/deploy.md` carries the sole-proprietor limits, the five variables and the canary the next person has to send by hand.

Forty-five tables, with Short as four columns on `shifts` rather than a table of its own (current state, ADR 0003). `orgs`; `idempotency_keys` (bookkeeping, not domain); Better Auth's `user`, `session` and `verification`, which alone carry no `org_id` and no policy, because identity is not org-scoped and Better Auth queries outside `forOrg`; and `volunteers`, `volunteer_accounts`, `volunteer_roles`, `volunteer_consents`, `release_versions`, `release_signatures`, `medication_authority`, `audit_entries`, `spaces`, `horses`, `horse_space_assignments`, `alerts`, `suppliers`, `products`, `feed_schedule_versions`, `feed_schedule_lines`, `horse_measurements`, `threshold_versions`, `weather_readings`, `weather_reading_hours`, `weather_condition_resolutions`, `shift_patterns`, `shift_pattern_roster`, `shifts`, `shift_roster`, `tasks`, `task_assignments`, `items`, `item_outcomes`, `shift_notes`, `attendance`, `announcements`, `contacts`, `standing_rules`, `observations`, `escalations`, `escalation_comments`, `days_of_supply_readings`, `reorders` and `reorder_comments`, which carry both like everything else will. `src/server/api/roster.test.ts`, `src/server/api/horses.test.ts`, `src/server/api/weather.test.ts`, `src/server/api/shifts.test.ts`, `src/server/api/checklist.test.ts`, `src/server/api/attendance.test.ts`, `src/server/api/announcements.test.ts`, `src/server/api/tick.test.ts`, `src/server/api/observations.test.ts`, `src/server/api/close.test.ts` and `src/server/api/supplies.test.ts` assert the policies against the catalogue, so a future table added without `enableRLS()` fails a test rather than leaking.

Three things about signing in that are easy to get wrong twice. **A session cannot outlive 400 days** — RFC 6265bis caps the cookie and browsers enforce it — so "permanent" is a year, and the _row_ is refreshed on use while the cookie is not: `ApiResponse` deliberately cannot carry a header (ADR 0020), so nothing applies Better Auth's refresh cookie and a volunteer signs in again about once a year. That is a known gap, written down in `src/server/auth/auth.ts`, and closing it is a question about the response layer. **`requestCode` mints and sends the code itself** rather than letting Better Auth's `sendVerificationOTP` do it: that path swallows the sender's failure and answers `sent: true` for a message that never left, which with email as the only channel (ADR 0009) is a volunteer standing in a barn waiting. And **`actorForUser` is where membership is decided** — a revoked Account and a removed Volunteer are both refused there, because that is the read every request makes and it is what makes removal bite on the next request rather than whenever something forces a refresh.

The stack is decided and is not open by default: TypeScript end to end, TanStack Start on Postgres 18 through Drizzle, deployed as one container (ADR 0007). Read `docs/adr/` before designing anything; the ADRs are decisions, not notes.

**The guardrails are armed, and they are not negotiable.** ADR 0016 puts six invariants in `eslint.config.ts` — under **seven** exemptions covering ten paths as of #33, and both counts are asserted by `npm run lint:fixtures`, so widening one breaks the build — and six more in the types of `src/server/api/route.ts` — a handler declares its authorization; a write's payload and key come from the contract rather than from the call site (ADR 0021), so a keyless write is unwritable; a mutation answers with an `ApiResponse`, which only `src/server/api/answer.ts` builds — `json` and `noContent` for a handler, `rebuild` for the replay, so a stored answer comes back exactly rather than approximately; every path and answer shape is one `src/shared/api-contract.ts` declares, on the server and on the phone alike; a write's authorization names a person, so the Board's cannot be spelled on one (ADR 0022); and a read's is settled by the session alone, so Shift Authority — half of which is a join against the `shiftId` a _payload_ names — cannot be spelled on one, while a write that does declare it must accept a `shiftId` (#40). A `PostToolUse` hook runs the six on every file write and blocks on a violation. There are no `eslint-disable` comments — `noInlineConfig` is on — and the only way to exempt code is a path override in `eslint.config.ts` with a reason. If a rule fires, the fix is the alternative its message names, never a way around it. The same hook also checks whatever file was just written, on any path, for a literal control byte — the one invariant that passes ADR 0016's test but is outside what an AST selector can see (#29); `npm run check:control-bytes` asserts the same repo-wide in `verify`.

**The local gate matches ADR 0007's description of it, as of its #27 amendment, and CI is no longer aspirational.** Husky's pre-commit runs Prettier on staged files through lint-staged; pre-push runs `npm run verify`. Prettier and ESLint do not fight — `eslint-config-prettier` turns off any stylistic rule that would disagree, though nothing in this config sets one yet. **`.forgejo/workflows/ci.yml` runs `verify` against a real Postgres 18 on every push and publishes an image from `main`; `deploy.yml` takes traffic and is dispatched by a person, never by a push**, because ADR 0007 makes migrations a deliberate step. The runner is on the OMV8 box at home, where Forgejo itself runs — which is ADR 0006's one factual error, amended there: the VPS never hosted the git host, so the shared-kernel risk that ADR listed does not exist. The whole of it, including what is deliberately still missing — backups, 1Password, SMTP, monitoring — is `docs/deploy.md`, and the stack the box runs is `deploy/`.

## Product

"Caballus" — a **mobile-first** application for horse rescue organizations. Primary users are volunteers working a shift in a barn, on a phone, often outdoors and possibly on poor connectivity. Data capture during a shift is the core loop; reporting and coordination are built on top of it.

## Domain model

Two entity clusters, and most features are joins between them.

**Horse** is the central record. It accumulates append-only logs across many care domains — feeding/nutrition, medical, dental, farrier, daily wellness, behavioral/training, emergency, adoption/foster/transfer, end-of-life. Design implications that recur across all of them:

- Care events are **historical logs, not current-state fields**. Feed changes, weight, body condition, medication, and training progress each need date + actor + reason, because "why did this change" is a real question rescues ask. Overwriting current state loses the answer.
- Many domains pair a **schedule** with a **history** and derive an **overdue alert** from the gap (vaccination, deworming, dental, farrier, grooming). That schedule/history/overdue triad is one pattern, not five — model it once.
- Fields that look required frequently aren't known. Date of birth is often unknown, so **age is derived when DOB exists and entered directly otherwise**. Assume incomplete intake data throughout.
- Photos attach to care events, not just to the horse (hoof records pre/post farrier, dental findings, memorial photos).
- Documents and compliance artifacts (Coggins, health certificates, adoption/foster/relinquishment agreements, test results) attach to the horse and have their own expiry/regulatory tracking.
- Audit logs are required for all record changes.

**Shift** is the other core entity, and it is where volunteers actually spend their time. A shift has a lead, a co-lead, volunteers, a start time, and a checklist. Two kinds:

- **Regular feed shifts** run a standard checklist: prepare food per horse, prepare/administer medication per horse, turn horses in/out, check real-feel temperature and act on it, hay and water in every paddock/field/stall (water heaters on when cold), muck paddocks and stalls, groom, fly spray, sunscreen, sweep barn.
- **Pop-up shifts** are ad-hoc (special feeding, hosing horses down in heat, welfare checks in adverse weather) and use **volunteer sign-up** rather than assignment.

Checklist items are **per-horse or per-area**, and some are **role-restricted** — food prep and medication are typically limited to the Feed Shift Lead or Co-Lead. Checklist completion is not a single boolean on the shift.

**Weather drives care decisions.** Real-feel temperature above or below a horse's threshold changes what happens on a shift: sheets/blankets in cold, fans in heat, horses kept in stalls at either extreme, water heaters on. Thresholds are per-horse. This means the app needs real-feel temperature as an input, not just a display.

**Shifts generate reports that route to roles.** A volunteer on a feed shift observing a medical, dental, or farrier issue reports it to the Head of Horse Welfare; a maintenance issue goes to the Head of Maintenance; low medicine/feed/supply levels trigger reorder. This observation → routed report → coordinator action flow is a first-class workflow, not an afterthought.

## Roles and permissions

Roles are the authorization model. **A volunteer may hold many roles simultaneously** — model this as a many-to-many assignment, never a single `role` column on a user.

- **President** and **Board Member** — can perform all functions for all roles.
- **Treasurer** — all financial matters.
- **Head of Maintenance** — sees and acts on maintenance and groundskeeping items.
- **Head of Horse Welfare** — sees and acts on medical/dental/farrier items; ingests issues reported from feed shifts, coordinates them back to volunteers, schedules visits.
- **Volunteer Coordinator** — new-volunteer orientation, assigning volunteers to shifts, removing volunteers from shifts or the rescue.
- **Feed Shift Lead** / **Feed Shift Co-Lead** — same responsibility set: set shift start time, food prep, medication, checklist completion, supervise volunteers, report medical/dental/farrier and maintenance issues upward, report low supplies.
- **Feed Shift Volunteer** — completes checklist items assigned to them by the Lead/Co-Lead.
- **Event Coordinator** — educational and public events (scout horsemanship badges, holiday events, open houses) and volunteer sign-up registration for them.

Permissions are scoped by **care domain** (medical/dental/farrier vs. maintenance vs. financial vs. volunteer management), which is why the two "head" roles and the Treasurer partition cleanly. Build authorization around domain scopes rather than enumerating per-endpoint role lists.
